# PROJECT.md — Spry monorepo

This file is the specification of the repository: what lives where, and the
contracts between the parts. It holds no implementation code. Anything an
agent generates in this repository is generated from this file, so a change
in design starts here.

## 1. Why one repository

Backend, frontend, database configuration, infrastructure and CI live in one
monorepo.

- **Atomic changes.** One commit changes the API and the client that calls it,
  so the two cannot drift apart.
- **The repository is the context window.** An agent working here can read
  the endpoint, the model, the migration and the component that renders it in
  one pass. Split across three repositories, it would see a third of the system
  and guess the rest, and a guessed contract is a bug found at integration.
- **The cost we accept.** No independent release cadence per part, and one
  CI pipeline for everything. For a team of four and a product that does not
  exist yet, shared context is worth more than independence.

## 2. Scope of this slice

- The backend exposes `GET /api/v1/meetings` (list) and `POST /api/v1/meetings`
  (create one).
- A meeting has: `id`, `title`, `starts_at`, `ends_at`, `attendee_count`.
- The frontend has one page that lists meetings, shows this week's totals
  against last week's, and has a form that adds a meeting.
- `docker compose up --build` is the only command a new developer runs, after
  installing Docker Desktop.

Out of scope, deliberately: authentication, organisations and teams, Google
Calendar sync, background workers, caching. No Redis, no queue, no reverse
proxy, no second database. Each arrives only when a requirement forces it.

### backend/

| Path | Purpose |
|---|---|
| `app/main.py` | App factory: CORS, the `/health` route, the API router |
| `app/config.py` | `Settings` from environment variables; nothing else reads `os.environ` |
| `app/db.py` | Async engine, session factory, the `SessionDep` dependency |
| `app/api/router.py` | Collects the v1 routers under `/api/v1` |
| `app/api/routes/` | HTTP layer only: parse, validate, call a service, shape the response |
| `app/schemas/` | Pydantic request and response models: the API contract in code |
| `app/services/` | Business logic and queries; no HTTP types here |
| `app/models/` | SQLAlchemy ORM models: the tables |
| `app/lambda_handler.py` | Entry point on AWS Lambda (function URL → ASGI; migrate action) |
| `migrations/` | Alembic: every schema change is a numbered, reversible revision |
| `scripts/entrypoint.sh` | Container start: `alembic upgrade head`, then Uvicorn |
| `tests/` | pytest against a real Postgres, each test in a rolled-back transaction |

### frontend/

| Path | Purpose |
|---|---|
| `app/layout.tsx`, `app/page.tsx` | The root layout and the single meetings page |
| `components/meetings-view.tsx` | Week-over-week cards and the meeting list |
| `components/meeting-form-dialog.tsx` | The "Add meeting" form |
| `components/ui/` | shadcn/ui components, generated by the CLI; not hand-edited |
| `lib/api.ts` | The only place that calls the API; zod schemas mirror §4 |
| `lib/meetings.ts` | Pure functions: durations, ISO weeks, week-over-week change |
| `tests/` | vitest + Testing Library; the API is stubbed on the `api` object |

Rule: nothing outside `backend/` imports its Python, nothing outside
`frontend/` imports its TypeScript. The only contract between them is §4.

## 4. API contract

Base path `/api/v1`. JSON only. Errors use FastAPI's shape, `{"detail": ...}`.
All timestamps are ISO 8601 **with an offset**. The API stores instants and
returns them in UTC.

| Method | Path | Body | Success | Errors |
|---|---|---|---|---|
| `GET` | `/health` | — | `200 {"status": "ok"}`, touches nothing | — |
| `GET` | `/api/v1/health/ready` | — | `200 {"status": "ok", "database": "ok"}` | `503` if Postgres does not answer |
| `GET` | `/api/v1/meetings?limit=50&offset=0` | — | `200 MeetingList` | `422` if `limit` ∉ 1..100 or `offset` < 0 |
| `POST` | `/api/v1/meetings` | `MeetingCreate` | `201 MeetingRead` | `422` on any rule below |

```text
MeetingCreate
  title           string, 1..200 characters
  starts_at       datetime with offset, e.g. "2026-11-02T10:00:00+02:00"
  ends_at         datetime with offset, later than starts_at
  attendee_count  integer, 1..1000

MeetingRead = MeetingCreate +
  id              uuid
  created_at      datetime, UTC

MeetingList
  meetings        MeetingRead[], ordered by starts_at, earliest first
  total           integer, all meetings regardless of limit/offset
```

Example `GET /api/v1/meetings` response:

```json
{
  "meetings": [
    {
      "id": "6f1c2b9e-1d1a-4a7e-9a55-2f3c8d0b7e41",
      "title": "Pricing sync",
      "starts_at": "2026-11-02T08:00:00Z",
      "ends_at": "2026-11-02T08:45:00Z",
      "attendee_count": 4,
      "created_at": "2026-10-28T19:12:03Z"
    }
  ],
  "total": 1
}
```

### Table `meetings`

| Column | Type | Rule |
|---|---|---|
| `id` | `uuid` | primary key, `gen_random_uuid()` |
| `title` | `varchar(200)` | not null |
| `starts_at` | `timestamptz` | not null, indexed |
| `ends_at` | `timestamptz` | not null, `ends_at > starts_at` |
| `attendee_count` | `integer` | not null, `>= 1` |
| `created_at` | `timestamptz` | not null, `now()` |

The rules are enforced twice on purpose: by the Pydantic schema, for a clear
`422`, and by database constraints, so no other writer can break them.

## 5. Docker Compose

Three services on one network, `spry`, and one named volume, `pgdata`.

| Service | Image | Port (host:container) | Depends on | Ready when |
|---|---|---|---|---|
| `db` | `postgres:17-alpine` | `5432:5432` | — | `pg_isready` succeeds (every 5 s, 10 tries) |
| `backend` | built from `backend/Dockerfile` | `8000:8000` | `db`, `condition: service_healthy` | `GET /health` answers (every 5 s, 12 tries, 20 s start period) |
| `frontend` | built from `frontend/Dockerfile` | `3000:3000` | `backend`, `condition: service_healthy` | — |

`depends_on` alone only orders the start. The `service_healthy` condition is
what makes the backend wait until Postgres actually answers. Later, if the
database disappears, the backend answers `/api/v1/health/ready` with `503` and
SQLAlchemy reconnects (`pool_pre_ping`) once it is back. No Compose feature
covers that part.

The backend applies migrations at container start, not at build time: the
image must not depend on a database that exists only at runtime.

`docker-compose.override.yml` is for development only: it selects the `dev`
build stages, bind-mounts the source, and runs `uvicorn --reload` and
`next dev`. `docker compose -f docker-compose.yml up --build` runs the
production images without it.

## 7. Conventions

- Schema changes only through an Alembic revision, never `create_all()` outside tests.
- Routes parse and validate, services hold logic, models own persistence.
- Async all the way: async sessions, `async def` handlers.
- `ruff check` and `ruff format` for Python; `eslint`, `prettier` and `tsc` for
  TypeScript. CI runs them on every push; red means the change is not done.
- Conventional Commits: `feat:`, `fix:`, `chore:`.
