## Status, honestly

The GCP Free Trial for a Ukrainian account requires a **$30 prepayment** before any billable
service (Cloud Run, Cloud SQL, Artifact Registry) can run, and I could not pay it. So Spry
runs on Google Cloud in the form that needs no billing account at all — the Firestore
option from Part 1 — and the Cloud SQL + Cloud Run target is written in Terraform:

| Piece | State |
|---|---|
| Frontend → Firebase Hosting | **deployed**: https://spry-yulia-2026.web.app |
| Database → **Cloud Firestore** (Spark plan, free quota) | **deployed**: collection `meetings`, access decided by `firestore.rules` (deployed with the site) |
| Reads and writes from the site | **work on Google Cloud**: the page lists meetings from Firestore, "Add meeting" and agendas write to Firestore (`frontend/lib/firestore.ts`, Firestore REST API) |
| Data | copied from the AWS database with `scripts/seed-firestore.mjs` (reads the AWS API, writes Firestore) |
| API → Cloud Run, DB → Cloud SQL, registry, secrets, service accounts | **written in Terraform (`gcp/`), not applied** — needs billing |
| HCP Terraform → GCP without keys (Workload Identity Federation) | written (`gcp-bootstrap/`) |

What this costs in design (see ADR 0008): with Firestore there is no API process on Google —
the browser talks to the database, and `firestore.rules` take the API's job of validating
input (types, lengths, `ends_at > starts_at`, only the agenda may change, nothing may be
deleted). That works for Spry today because the AWS API has no sign-in either; once sign-in
exists, the rules would check `request.auth`, or the API on Cloud Run comes back.

## Part 2 — what moving the core means in code

- `backend/scripts/entrypoint.sh`: listens on `${PORT:-8000}` — Cloud Run sends HTTP to `$PORT`.
- The image for Cloud Run is the existing `runtime` stage of `backend/Dockerfile`; the
  `lambda` stage (AWS base image + handler) is simply not used. Same image runs in Compose.
- `DATABASE_URL` points at the Cloud SQL connector socket:
  `postgresql+asyncpg://spry:…@/spry?host=/cloudsql/<connection-name>`, stored whole in
  Secret Manager, generated by Terraform (`random_password`), never in the repository.
- Data for Cloud SQL (target): Alembic migrations run against the empty database on
  container start (the AWS data is test data, so no `pg_dump`). Data for Firestore
  (deployed): `node scripts/seed-firestore.mjs https://api.yulia-spry.xyz` copies the
  meetings and their agendas from the AWS API.
- Firestore build: `GCP_API_MODE=firestore make deploy-firebase` sets
  `NEXT_PUBLIC_DATA_SOURCE=firestore`, so `lib/api.ts` swaps its three calls for
  `lib/firestore.ts` — the components did not change at all.
- `firebase.cloudrun.json` is the target hosting config: `/api/**` → Cloud Run `spry-api`,
  one origin, no CORS (what CloudFront did in front of the API).
- Deploy: `make gcp-bootstrap` (once) → `make gcp-image` → `make gcp-init` → `terraform -chdir=gcp apply`
  → `GCP_API_MODE=cloudrun make deploy-firebase`. Stop the database: `make sql-stop`.

## Part 3 — cost: the minimal setup on both clouds

On-demand list prices, USD, 730 h/month, no tax. AWS us-east-1, GCP us-central1.
AWS is Spry **as deployed** (RDS, not Aurora — the Free plan does not allow Aurora).
Today's real AWS bill is $0, covered by Free plan credits; the table is what it would cost without them.

**Assumptions.** *Nobody*: no requests. *Class demos*: 10 × 2 h = 20 h of light use.
*Office hours*: 8 h × 22 days = 176 h of light use. Light use stays inside the free
tiers of Lambda (1 M requests, 400 000 GB-s) and Cloud Run (2 M requests, 180 000 vCPU-s,
360 000 GiB-s). *Busy around the clock*: 10 requests/s all month (26.3 M requests),
200 ms each, 512 MB. Frontend, registry, secrets and logs are $0 or cents on both sides.

### Spry's core, nobody using it for a month (the reference table, for this project)

| Piece | AWS (Spry as deployed) | Google Cloud (this lab, `gcp/`) |
|---|---|---|
| Frontend + CDN + HTTPS | CloudFront Free plan → $0 | Firebase Hosting free plan → $0 |
| API | Lambda, idle → $0 | Cloud Run, scaled to zero → $0 |
| Database compute | RDS `db.t4g.micro` running, $0.016/h → $11.68 | Cloud SQL `db-f1-micro` running, $0.0105/h → $7.67 |
| Database storage | 20 GB gp2 at $0.115/GB → $2.30 | 10 GB SSD at $0.17/GB → $1.70 |
| Registry, secrets, logs | ECR + 1 secret ($0.40) + logs ≈ $0.50 | within the free tier (0.5 GB registry, 6 secret versions) |
| **Total** | **≈ $14.50 / month** | **≈ $9.40 / month, or ≈ $1.70 with the instance stopped** |

### Spry's core per profile

| Profile | AWS: Lambda + RDS `db.t4g.micro` 24/7 + 20 GB gp2 | GCP: Cloud Run + Cloud SQL `db-f1-micro` 24/7 + 10 GB SSD | GCP: Cloud SQL stopped when unused | GCP: Firestore instead of SQL |
|---|---|---|---|---|
| Nobody | $11.68 + $2.30 + ~$0.50 ≈ **$14.50** | $7.67 + $1.70 ≈ **$9.40** | $1.70 | **$0** |
| Class demos (20 h) | ≈ **$14.50** | ≈ **$9.40** | $0.21 + $1.70 ≈ **$1.90** | $0 |
| Office hours (176 h) | ≈ **$14.50** | ≈ **$9.40** | $1.85 + $1.70 ≈ **$3.55** | $0 |
| Busy 24/7 | $14.50 + Lambda $42 ≈ **$56** | $9.40 + Cloud Run $71 ≈ **$80** | ≈ $80 (cannot stop) | Cloud Run $71 + reads ~$15 ≈ **$86** |

How the busy line is built — Lambda: (26.3 M − 1 M) × $0.20/M = $5.06 requests +
(26.3 M × 0.2 s × 0.5 GB − 0.4 M) GB-s × $0.0000166667 = $37.13 → $42.
Cloud Run (one instance, request-based billing, concurrency covers 10 req/s):
(2 628 000 − 180 000) vCPU-s × $0.000024 = $58.75 + (1 314 000 − 360 000) GiB-s × $0.0000025
= $2.39 + (26.3 M − 2 M) × $0.40/M = $9.71 → $71. RDS `db.t4g.micro` is $0.016/h = $11.68/month,
gp2 $0.115/GB-month; Cloud SQL `db-f1-micro` $0.0105/h, SSD $0.17/GB-month.

**Which cloud is cheaper, and which line decides it?**
For the first three profiles **Google Cloud** is cheaper, and the deciding line is the
**database instance**: Cloud SQL `db-f1-micro` costs less per hour than RDS `db.t4g.micro`
and, stopped, costs only its storage. (Against Lab 4's paused Aurora, ≈ $0.30, AWS would win
these profiles — the line is the same, the answer flips.) For *busy 24/7* **AWS** is cheaper,
and the deciding line flips to **API compute**: at a steady load Lambda's per-request GB-seconds
cost less than a Cloud Run instance that is busy the whole month.

**Where is the GCP equivalent of the Aurora trap?** Aurora cost more than an instance when
something kept it from pausing. On GCP the database has nothing to pause at all: **Cloud SQL
runs and bills 24/7 unless someone stops it**, and a stopped instance still bills its SSD.
On the compute side the trap is **Cloud Run with `min_instance_count ≥ 1` or CPU always
allocated** (instance-based billing): one forgotten setting turns $0 into ~$60/month.
`gcp/` sets `min_instance_count = 0`, `cpu_idle = true`, `max_instance_count = 2`.

## Part 4 — what else Google Cloud is good at

Screenshots attached: BigQuery query, Looker Studio chart, OCR result.

- **BigQuery** (sandbox, no card), project `spry-yulia-2026`: top 10 US baby names since 2000
  over `bigquery-public-data.usa_names.usa_1910_current` (Jacob 454 809, Michael 414 711,
  Emma 407 365 …). **Bytes processed: 143.71 MB, billed 144 MB, 371 ms** — about 0.014 % of
  the free 1 TiB a month. BigQuery read only the three columns the query uses.
- **Looker Studio** (now "Data Studio" / Центр даних): "Open in → Data Studio" from the query
  result, a column chart of `total` by `name` next to the table.
- **OCR**: Cloud Vision text detection ("Try the API" demo) on a photo of my handwritten
  statistics notes. It found the page → blocks → words and read most of it correctly
  ("1) Statistical", "hypothesis testing", "assertion distribution of one"), but misread the
  heading "Topic 11" as "Tople 11" and broke joined handwriting into fragments. The demo
  accepts only JPEG/PNG — the iPhone HEIC photo had to be exported to JPEG first.

Not done, because they need billing: the Dataflow "Cloud Storage Text to BigQuery" template
and the agenda prompt in Vertex AI Studio (the same prompt runs in Google AI Studio for free).

**When is a specialised service like Document AI better than a general LLM?** The OCR demo shows
both sides: Vision returned every word with its box and position (exactly what a form or
receipt pipeline needs), but it does not understand that "Tople" must be "Topic". When the job
is fixed and repeated at volume — the same invoice or form, thousands of pages: per-page
price ($1.50 / 1 000 pages for OCR), bounding boxes and confidence scores, deterministic
output, no prompt to drift. When it is not: free-form text that needs understanding — Lab 6's
pasted agenda has no layout to parse, it needs the meaning ("Q4 numbers, 10 min, Anna"), and
an LLM with a schema does that in one call; Document AI would only return the same text back.

**Lab 8 on Google Cloud.** S3 → **Cloud Storage**; Glue Crawler + Data Catalog + Athena →
**BigQuery** (external table over the JSON, then a native partitioned table instead of the
Parquet CTAS — BigQuery stores columnar data itself); the nightly Glue job → **Dataflow**
(the same Beam code for the batch and for the stream); Kinesis + Firehose → **Pub/Sub** with
a BigQuery subscription; the local Redpanda consumer → a streaming **Dataflow** job;
dashboards → **Looker Studio**. What I would no longer manage: partitions (`MSCK REPAIR`),
crawler schedules, the Parquet copy and its prefix, Athena's result bucket, Firehose buffering.

## For the class discussion

- **Lock-in.** Moved without changes: the FastAPI code, the Docker image (`runtime` stage),
  the Next.js export, the SQL schema and migrations. Changed: one line in `entrypoint.sh`
  (`$PORT`) and the `DATABASE_URL` format. Rewritten: all the infrastructure code
  (CloudFormation/aws → google provider) and IAM. So the lock-in is not in compute, it is in
  the managed services around it — IAM, secrets, the CDN, and Bedrock — and it would be in
  data if we had chosen Firestore.
- **Multicloud.** Today's state (page on Google, API and data on AWS) works, but every page
  load crosses clouds, AWS egress is billed per GB, and there are two consoles, two IAM
  models and two bills. For Spry it is a migration state, not a goal; it makes sense only
  for one service that is much better on the other cloud (BigQuery, a model).
- **Scale to zero.** Giving up SQL for ~$9/month is worth it for a demo nobody uses or data
  that is naturally documents; it is a bad trade when the data is relational, the queries are
  ad hoc, or the team would spend more hours on the rewrite than it saves in a year.
- **Choosing a cloud.** At this size the price difference is a few dollars; what decides is
  what the team already knows, the credits and billing rules (this lab: a $30 prepayment
  stopped the whole GCP side), and the services around the API — BigQuery on GCP, Bedrock's
  model choice on AWS.
